# TickScope Multi-Broker化 改善計画書

## 1. 改善の目的

TickScopeの現行設計は、基本アーキテクチャとして「2つのMT5 / 2 Broker」を前提としている。

一方、現在の `docs/improvement.md` では、すでに以下の思想が導入されている。

* Brokerを固定A/BではなくN Brokerとして扱う
* Pairwise Analysis
* Multi-Broker Analysis
* Consensus
* Dispersion
* Burst
* Broker Behaviour
* Feed Quality
* Observed Lead/Lag

このため、今後の設計の中心を明確に、

> **「2社を比較するアプリ」ではなく、「複数FX BrokerのリアルタイムFeedを同時観測し、Broker間の差異・一致・更新特性・観測上の先行遅行を分析するマーケットデータ観測ツール」**

へ変更する。

2社比較は廃止しない。

**2社はMulti-Brokerシステムの最小構成として扱う。**

---

# 2. 改善後のプロダクト定義

## 2.1 現行

```text
2社のFX BrokerからMT5 Tickを取得
        ↓
2社を比較
        ↓
価格差・Spread・Lead/Lagを表示
```

## 2.2 改善後

```text
N社のFX BrokerからMT5 Tickを取得
        ↓
Broker State
        ↓
┌──────────────────────────┐
│ Multi-Broker Analysis    │
│                          │
│ Consensus                │
│ Median / Range           │
│ Dispersion               │
│ Freshness                │
│ Breadth                  │
│ Burst                    │
│ Outlier                  │
│ Feed Behaviour           │
└──────────────────────────┘
        +
┌──────────────────────────┐
│ Pairwise Analysis        │
│                          │
│ A-B                      │
│ A-C                      │
│ A-D                      │
│ B-C                      │
│ ...                      │
└──────────────────────────┘
        ↓
        UI
```

Multi-Broker Analysisを上位概念とし、Pairwise Analysisはその下位機能とする。

# 3. 改善の基本原則

## O1. Multi-Broker First

TickScopeのすべての主要設計はN Brokerを前提とする。

```text
Broker A
Broker B
Broker C
Broker D
...
Broker N
```

2 Brokerは特殊ケースではなく、

```text
N = 2
```

として自然に処理されること。

---

## O2. Pairwiseは残す

2社間比較自体には明確な価値がある。

例えば、

```text
OANDA ↔ Axiory
```

だけを細かく比較する用途は残す。

ただし、

> 「2社比較画面」

をアプリ全体の主要概念にはしない。

Pairwise AnalysisはMulti-Broker Coreから生成される分析ビューとして扱う。

---

## O3. Reference Brokerを市場の真値とみなさない

Reference Brokerを設定可能としても、

```text
Reference = Market Truth
```

とは扱わない。

ReferenceはUI上の比較基準にすぎない。

---

## O4. ConsensusをMarket Truthとみなさない

3～5社が同方向に動いたからといって、それを

```text
市場の真値
```

とは表現しない。

Consensusはあくまで、

> 複数Broker Feed上で観測された一致度

として扱う。

---

## O5. Brokerを総合Scoreで順位付けしない

以下は禁止する。

```text
Broker A = 92
Broker B = 81
Broker C = 70
```

のような総合ランキング。

代わりに、

```text
Responsiveness
Freshness
Spread Stability
Quote Stability
Consensus Alignment
Repricing Behaviour
Outlier Frequency
Stale Frequency
Observed Lead Frequency
Observed Follow Frequency
```

のような複数の観測軸を分離する。

---

## O6. 観測と解釈を分離する

画面上の情報は、

```text
Observed
Derived
Hypothesis
```

を分離する。

例えば、

### Observed

```text
Broker A Mid +2.0pt
Broker B Mid +1.8pt
Broker C Mid +2.1pt
```

### Derived

```text
Median +2.0pt
Range 0.3pt
Breadth 3/3
```

### Hypothesis

```text
A/B/Cで同時的なRepricingが観測された
```

とする。

「これは市場が上昇した」というような外部世界の断定はしない。

---

# 4. 最重要の設計変更

現行設計には以下のA/B固定が残っている。

* Broker A / Broker B
* Port A / Port B
* A/B固定のCandleView
* A/B固定のMetricsView
* A/B固定のUiSnapshot
* A/B固定のHealth管理
* Receiver A / Receiver B
* A/B固定の設定schema

これらをN Brokerモデルへ移行する。

# 5. Broker Model

## 5.1 BrokerId

現在：

```rust
BrokerId = A / B
```

という概念が強い。

改善後：

```rust
pub struct BrokerId(u32);
```

を基本型とする。

初期設定として、

```text
1 = OANDA
2 = Axiory
3 = Tradeview
4 = Dukascopy
5 = JFX
```

などを設定可能にする。

ただしBroker固有情報をコードへハードコードしない。


各Brokerについて最低限、

```text
last_mid_change_mono_ns
```

を保持する。

# 8. Multi-Broker Analysis

Multi-Broker AnalysisをTickScopeの主要分析層とする。

## 8.1 Consensus

複数Brokerの価格変化方向を集計する。

例：

```text
A UP
B UP
C UP
D UP
E FLAT
```

表示：

```text
UP  4 / 5
DOWN 0 / 5
FLAT 1 / 5
```

これは売買シグナルではない。

---

## 8.2 Median

新しい価格状態の代表値として、

```text
Broker Mid
```

からMedianを計算する。

ただし、

```text
Median = 真の市場価格
```

とは扱わない。

名称も必要に応じて、

```text
Observed Broker Median
```

などとする。

---

## 8.3 Range

```text
max(mid) - min(mid)
```

によってBroker間の価格分散を見る。

---

## 8.4 Dispersion

複数Brokerがどれだけ一致しているかを観測する。

3～5 Brokerでは、

```text
Median
Range
Pairwise deviation
```

を基本とし、過度に複雑な統計モデルを持ち込まない。

---

## 8.5 Freshness

Brokerごとの最新Quoteの鮮度を表示する。

例：

```text
A  2ms
B  4ms
C  3ms
D  812ms
```

Dだけ長時間更新されていない場合、

```text
STALE
```

として扱う。

価格停止とFeed Staleを混同しない。

---

## 8.6 Outlier

複数Brokerから明らかに乖離しているBrokerを観測する。

例えば、

```text
A 158.200
B 158.201
C 158.200
D 158.203
E 158.200
```

なら、

```text
D = observed outlier
```

という情報を提供できる。

ただし、

```text
Dが間違っている
```

とは断定しない。

---

## 8.7 Burst

複数Brokerで短時間に連続した価格変化が発生した場合、それをEvent Clusterとしてまとめる。

例：

```text
A UP 0ms
B UP 4ms
C UP 7ms
D UP 9ms
```

を1つのBurstとして観測する。

---

# 9. Pairwise Analysis

PairwiseはMulti-Brokerの補助的かつ重要な分析機能として残す。

N Brokerなら自動的に、

```text
N × (N - 1) / 2
```

Pairを生成可能とする。

5 Brokerの場合：

```text
A-B
A-C
A-D
A-E
B-C
B-D
B-E
C-D
C-E
D-E
```

---

# 10. Focus Pair

UIでは全Pairを常時表示しない。

ユーザーが、

```text
Broker A
↕
Broker C
```

のように2Brokerを選択し、詳細比較できる。

表示対象：

```text
Bid Difference
Ask Difference
Mid Difference
Spread Difference
Observed Lead/Lag
Quote Update
Tick Interval
```

これを`Focus Pair`とする。

これにより、2社比較機能を維持しつつ、アプリの中心概念をMulti-Brokerにできる。

# 13. Lead/Lag設計

Lead/Lagは維持する。

ただし、

> Broker Aが市場を先導した

とは表現しない。

正確には、

> **このPC上でBroker Aの対応する価格変化がBroker Bより先に観測された**

とする。

---

# 14. Multi-Broker Lead/Lag

2社の場合：

```text
A → B
```

でよい。

3社以上の場合：

```text
A @ 0ms
B @ 4ms
C @ 7ms
D @ 9ms
```

のようなEvent Clusterへ拡張する。

重要なのは、

```text
A → B
A → C
A → D
```

を単純に3つの独立Eventとして扱うのではなく、

```text
One Market/Feed Observation Cluster
```

として認識すること。

# 16. Broker Advantageの再定義

「Broker Advantage」という名称は、売買上の優位性を想起させる可能性があるため慎重に扱う。

```text

```


# 19. Pairwise計算量への対策

Pair数は、

```text
N(N-1)/2
```

で増加する。

そのため、

## Current State

Pairwiseを必要なBroker組み合わせだけ計算できる構造にする。

例えば、

```text
Focus Pair
```

は常時計算。

その他Pairは、

```text
画面表示用
履歴解析用
必要時
```

に限定できる設計にする。

ただし、実装上過度な最適化は初期段階では行わない。

5 Broker程度なら全Pair計算を基本とし、性能測定結果で必要なら最適化する。

# 35. 製品コンセプト

TickScopeは、

> 「どのBrokerが勝者かを決めるアプリ」

ではない。

また、

> 「市場を予測するアプリ」

でもない。

TickScopeの目的は、

> **複数BrokerのリアルタイムFeedを同時観測し、単一Brokerだけでは見えにくい価格差、Quote更新、Freshness、Spread、Dispersion、Burst、Observed Lead/Lagなどを、人間が高速に把握できるようにすること**

とする。

# 37. 開発者への最重要指示

### 1.

**TickScopeをA/B固定のアプリとして新たに拡張しない。**

### 2.

新規実装では、Brokerを必ず`BrokerId`で識別する。

### 3.

2 Brokerは特殊ケースではなくN=2として処理する。

### 4.

Pairwise AnalysisはMulti-Broker Coreの下位機能として実装する。

### 5.

UIの中心は「2社比較」ではなく「Broker Overview」にする。

### 6.

Reference Brokerを市場真値として扱わない。

### 7.

Consensusを市場真値として扱わない。

### 8.

Brokerの総合Scoreや順位付けを作らない。

### 9.

Observed / Derived / Hypothesisを区別する。

### 10.

Raw Tick PathはBroker数が増えてもlossless設計を維持する。

### 11.

UI Snapshotだけは最新状態優先でcoalesce可能とする。

### 12.

Broker数増加によるp95/p99 latency regressionを常に測定する。

### 13.

5 Brokerを重要Regression Test対象にする。

### 14.

Multi-Broker化によって既存2 Brokerの正確性を損なわない。

```text
[ ] Raw Tick保存がBroker数に依存しない
```

# 39. 改善後の最終コンセプト

TickScopeは、

```text
2 Broker Comparison Tool
```

ではなく、

```text
Multi-Broker Real-Time Market Data Observatory
```

として設計する。

その中に、

```text
Multi-Broker Analysis
        +
Pairwise Analysis
```

を持たせる。

この構造なら、

```text
2 Broker
3 Broker
4 Broker
5 Broker
```

とBroker数が増えてもアプリの基本概念が変わらない。

また将来的に、

```text
Feed Behaviour
Historical Behaviour
Replay
Event Cluster
Microstructure Analysis
```

を追加する場合も、現在のTick/Engine/Projectionアーキテクチャを維持したまま拡張できる。

したがって、今後のTickScope開発では、

> **「2社比較機能を高機能化する」のではなく、「Multi-Broker Coreを完成させ、その上に2社比較を含む各種観測ビューを構築する」**

ことを基本方針とする。
