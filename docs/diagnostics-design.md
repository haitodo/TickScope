# 低負荷診断・性能計測

通常のトレード経路では計測、診断ファイル、raw frame保存を起動しない。調査時だけ起動引数で必要な機能を有効にし、計測の出力が受信・ACK・エンジン処理を待たせない構成にする。

## 起動モード

| 起動 | コンソールログ | raw frame保存 | 性能計測 |
|---|---:|---:|---:|
| 通常起動 | なし | なし | なし |
| `-c` / `--console` | あり | なし | なし |
| `-d` / `--diagnostics` | なし | なし | 有効 |
| `-r` / `--record-raw` | なし | 有効 | なし |
| `-d -r` | なし | 有効 | 有効 |
| `-c -d -r` | あり | 有効 | 有効 |

`-d` と `-r` は独立している。`-d` はraw保存を行わず、本番経路に近い負荷で計測する。`-r` はTLOG raw frameを保存する。`-d -r` の計測値には保存処理の負荷が含まれ、通常時の基準値としては使わない。`-c` はテキストログのコンソール表示だけを制御する。

`[logger].enabled` の既定値は `false`。`-r` でraw保存を有効にする。既存の設定ファイルで `[logger].enabled = true` を明示している場合も、従来どおりraw保存を有効にする。設定ファイルの `logger.log_dir` は保存先を指定し、診断CSVは `data/diagnostics` にrunごとに作成する。

## `-d` の出力

診断ファイル名は `data/diagnostics/run_<run-id>.csv`。計測サンプルは固定長の有界チャンネルに非ブロッキングで送り、別スレッドが1秒ごとのCSV行にまとめる。サンプルごとの文字列化・ファイル書き込み・同期I/Oは行わない。チャンネル容量は8192サンプル、各ステージの分位計算は直近2048サンプルを使う。計測キューが満杯なら処理を待たずにサンプルを落とし、`metric_samples_dropped` 行に件数を記録する。

CSVにはrun ID、raw保存の有無、ACK境界をヘッダーに記録する。raw TLOGと診断CSVは同じrun IDを使うため、`-d -r` で両方を保存した場合に対応づけられる。各行はステージごとのサンプル数、分位計算に使った件数、p50/p95/p99/最大値をマイクロ秒で持つ。

計測ステージは次のとおり。

- `tcp_receive_to_ingress`: ソケットreadの観測時刻からingress受付まで。raw保存を有効にした場合は保存時間も含む。
- `raw_persistence`: rawフレームの永続保存処理にかかった時間。`-r` または設定によるraw保存時だけ記録する。
- `tcp_receive_to_ack`: ソケットreadの観測時刻からACK書き込み完了まで。
- `batch_ack_write`: ACKのソケット書き込み時間。
- `ingress_to_engine`: TickBatchのソケットread観測時刻から、merge処理後にエンジンがそのバッチを処理するまで。
- `engine_frame_processing`: 1フレームのエンジン処理時間。
- `projection_build`: エンジンロック待ちを含むProjection構築時間。
- `snapshot_build`: UI Snapshotの構築時間。
- `snapshot_to_ui`: Snapshot生成から、UIがそのSnapshotを初めて描画処理に渡すまで。
- `ui_render_work`: eguiの1回分のUI構築・描画指示処理時間。GPU表示完了時刻ではない。

単調時計の境界をまたぐ区間だけを比較する。`tcp_receive_to_ingress` などのread時刻はTickScopeがread後に採った観測時刻であり、NIC到着時刻ではない。EAとWindows間の時計差から片道ネットワーク遅延を推定しない。

## ACKとデータ保持

raw保存が無効な場合、ACKはフレームがTickScopeの揮発性ingress queueに受け付けられたことを示す。EAはACKが一致するまで未確認バッチをメモリに保持して再送できるが、ACK後にTickScopeが異常終了し、エンジン処理前のデータが残っていた場合、そのデータを失う可能性がある。

raw保存が有効な場合、フレームを同期保存してからingress queueへ送り、受付後にACKを返す。TLOGには受信内容が残るが、現行アプリは起動時にTLOGを読み戻してTickEngineを復旧しない。したがって、これはraw記録の永続化であって、プロセス再起動後の自動復旧やend-to-endの欠損ゼロ保証ではない。そこまで必要なら、サーバー側の重複排除付き再生とEA側の永続outboxを別途実装する。

raw保存OFFのTCP経路では、デコーダーがフレーム単位のrawバイト列を複製・保持しない。ingressのメモリ上限計算にはヘッダーのwire長を使う。raw保存ONの場合だけ元のwire bytesをTLOGに保持する。

## 負荷比較

通常経路の低負荷計測には `-d` を使う。rawデータとの因果関係も必要な調査には `-d -r` を使い、raw保存の同期I/Oを含む測定値として扱う。`-d` 自体にも時計読み取りと非ブロッキング送信の負荷はあるため、通常起動との比較は同じ端末・同じ負荷条件で行う。

次に広げる場合は、フレーム欠損・重複・再接続・EA履歴取得失敗などの正確なカウンターを同じ有界方式で追加し、Debug画面に集計値を表示する。全ティックのJSON/CSVログを通常経路に追加しない。
