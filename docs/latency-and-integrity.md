# レイテンシとデータ完全性

## 実装した改善

- EAのACK確認・履歴取得タイマーを、250msのハートビート周期から分離した。`InpCollectionIntervalMs` の既定値は10ms。`OnTick` でも引き続き収集する。MT5の実際のタイマー分解能は通常10〜16ms程度で、指定間隔どおりの実行を保証しない。
- TCP接続中はsleepポーリングをやめ、タイムアウト付きのブロッキングreadで到着時に起床する。ACK送信にもタイムアウトを設ける。
- 受信時刻はread直後に採取し、そのreadで完成した各フレームに使う。後続フレームの時刻に復号やディスク同期の時間を加算しない。これはアプリケーションの観測時刻であり、NIC到着時刻ではない。
- 受信済みフレームの消費位置を保持し、フレームごとの残りバッファ移動とTickBatchの複製を除去した。
- スナップショット構築時間を描画周期の予算に含め、構築後にさらに丸一周期待つ動作を除去した。
- 単一ログレコードがキューのバイト上限を超える場合はエラーを返す。容量が永久に空かないリトライを防ぐ。
- CopyTicksの失敗・部分取得エラー・カーソル上限到達を、ウォームアップ完了として扱わない。

## 維持する保証と限界

通常起動ではraw保存を行わず、ACKはingress queueへの揮発性受付後に返す。`-r` または `[logger].enabled = true` でraw保存を有効にした場合は、rawフレームのディスク同期とingress受付の両方が完了してからACKを返す。どちらのモードでもEAは正しいACKを受け取るまで未確認バッチとカーソルを保持する。

raw保存を有効にした場合、ディスク同期時間とEAのACK確認間隔がスループットに影響する。通常起動は同期I/Oを省く代わりに、ACK後からエンジン処理までの間にTickScopeが異常終了すると、ingress内のデータを失う可能性がある。どちらのモードもEA自体の終了をまたぐ未確認バッチの永続化や、ブローカーからMT5に届かなかったティックの復元を保証しない。

`-d, --diagnostics` はraw保存を伴わない低負荷計測、`-r, --record-raw` はraw frame保存、`-d -r` は両方を有効にする。計測CSVはrun単位で `data/diagnostics` に保存され、raw TLOGと同じrun IDを使う。raw保存OFFの通常経路では、デコーダーもフレームごとのrawバイト列の複製を省く。詳しくは [低負荷診断・性能計測の設計](diagnostics-design.md) を参照。

表示は既定60HzのスナップショットとGUI描画の周期にも制約される。各ティックを処理・保存していても、すべての途中状態が画面に1枚ずつ表示されるわけではない。

## 実機での評価

既存の回帰テストはプロトコル、ACK、再接続、保存、ローソク足、UIなどを扱う。計測モードの実性能は、releaseビルドと更新したEAを用い、平常時・指標発表時に `-d` と通常起動を同じ条件で比較して確認する。`-d -r` の値は同期保存コスト込みで別に評価する。

Rustの処理経路計測だけでは、MT5の取得からTickScopeの表示までの全遅延や欠損ゼロは断定できない。EAのCopyTicks取得・ACK確認、TickScopeの診断CSV、sequence gap、CPU負荷、raw保存時の同期時間を実端末で合わせて確認する。
